# Harness - how this skill is enforced

This skill is long because UI work has many ways to go wrong. Agents skip steps when a task "looks simple": they read one file, fix what they noticed, and call it done. The harness below stops that by making every step leave a file behind, and by not letting the next step start until the previous file is complete. **The files are the proof of work. No file, no step.**

**Violating the letter of these rules is violating the spirit of them.** "I did it in my head" or "I checked, there was nothing" without the file entry counts as not done.

## 1. The ledger folder

Create `.ui-audit/<surface-slug>/` at the start (add `.ui-audit/` to `.gitignore` if the user doesn't want it committed - ask once). Files, in the order they're written (audit shape follows W3C WCAG-EM: scope → explore → sample → evaluate → report):

| File | Written in | Must contain (required slots) |
|---|---|---|
| `00-scope.md` | Phase 0 | the user's request **verbatim**; mode (FOCUSED / FULL); the target surface (route + entry file); for FOCUSED: the named issues as a numbered list, and which catalog categories they map to |
| `01-design.md` | Phase 1 | DESIGN.md path(s) or "none"; the digest table; Gaps list; conflicts; app archetype (SaaS / internal tool / consumer) & audience profile; mandatory external domain research benchmarks |
| `02-inventory.md` | Phase 1 | every file in the surface with: role, states it handles, **Read: ✔** (each file must be read in full - not grepped) |
| `03-findings.md` | Phase 1 | the findings ledger (§3). Every finding has an ID |
| `04-coverage/` | Phase 1 (FULL only) | five section reports generated by `verify_ledger.mjs init` (§4): every catalog rule ID, in order, with a `PASS` / `VIOLATION` / `N/A` row and machine-checkable evidence |
| `PLAN.md` | Phase 2 | the plan (plan-template.md) incl. token ledger, flow tables, chosen direction, **Revision log**; every finding ID appears in exactly one slice or in "Deferred" with a reason |
| `05-progress.md` | Phase 4 | per slice: files changed, finding IDs closed, deviations, checks run with their output, commit SHA |
| `06-verify.md` | Phase 5 | per finding ID: how it was verified (command output, file:line re-read, screenshot); final checklist results |

Write the files as you go, not at the end. Update the finding status in `03-findings.md` the moment a fix lands.

## 2. Gates

Before starting each phase, open the previous files and check the gate. If a gate fails, go back; do not "carry on and fill it in later".

| Gate | Condition to pass |
|---|---|
| G0 → Research | `00-scope.md` has the verbatim request, a mode, and a target surface |
| G1 → Plan | `verify_ledger.mjs check <surface> --gate g1` prints PASS (it re-opens the source: inventory files exist and are marked Read ✔, every finding's quoted evidence is at its `file:line`, every catalog rule has exactly one row in catalog order, every `PASS` quote is found within 5 lines of its cited line, every `N/A` regex matches nothing in the inventory); `01-design.md` has a digest or "none", the archetype and audience profile and the external research benchmarks; FOCUSED: every named issue has ≥1 finding or a "could not reproduce - evidence" line, and the check runs with `--categories` for the mapped categories |
| G2 → Approval | `verify_ledger.mjs check <surface> --gate g2` prints PASS (every finding placed, section 4b present, exactly one concept, no colour literal outside the token ledger, every `data-trace` in the inventory, every `data-copy` verbatim from its cited line, no filler); flow tables with friction lines (user-flow.md) or `N/A: single-screen, no state change`; wireframes if layout changes |
| G3 → Implement | the user approved **a specific concept revision** in this conversation (quote their words and `Approved rev N` in `PLAN.md` under "Approval"); any tweak after that reopens the loop (interactive-prototypes.md §6) |
| G4 → Verify | every slice in `05-progress.md` has its checks run with output pasted and a commit SHA |
| G5 → Done | `verify_ledger.mjs check <surface> --gate g5` prints PASS (zero `open` findings; every `fixed` finding has a `path:line "quote"` of the new code that is really in the file and its old evidence is gone; every slice has a commit SHA git knows); typecheck/lint/tests ran in this message and passed or pre-existing failures are named |

State the gate result by pasting the script's last line (`Gate G1 script: PASS - 14 files, 322 rules (...), 23 findings, 0 errors`) plus one line on research done. A gate line without the script output is not a gate result.

## 3. Finding format and the proof rule

`03-findings.md` is one table:

```markdown
| ID | Rule | Where | Problem (evidence) | Fix | Sev | Status |
|---|---|---|---|---|---|---|
| F-001 | MUT-03 | components/invoice-form.tsx:88 | `onSubmit` has no pending guard; `mutate()` can fire twice (no `disabled`, no `isPending` check) | Button `loading={isPending}` + early return | P1 | open |
```

**Severity is rated in a second pass, not during the hunt.** Record findings severity-free first (leave Sev blank), then rate the complete list against frequency × impact × persistence: how often it hits, how hard it is to overcome, whether it repeats (Nielsen). P0 ≙ catastrophe (blocks task / loses data · fix before release), P1 ≙ major (broken or WCAG A/AA failure), P2 ≙ minor (wrong or confusing), P3 ≙ cosmetic (polish if time). `rejected` ≙ not-a-problem. Rating during the hunt biases the audit toward what was found first; the list gets rated whole.

- **ID**: `F-001`… never reused.
- **Rule**: the ID from `rule-catalog.md` (or `DM-<n>` for a DESIGN.md rule, cited by section).
- **Where**: file:line. One finding = one root cause (list extra locations in the same row).
- **Severity**: rated in the second pass (above): P0 blocks a task / loses data · P1 broken or WCAG A/AA failure · P2 wrong or confusing · P3 polish.
- **Status**: `open` → `fixed` | `deferred` | `rejected`.

**The proof rule.** A candidate becomes a finding only when it has:
1. **Rule** - a catalog rule or DESIGN.md rule it breaks (not taste).
2. **Evidence** - the exact code (quote it) or rendered result showing the problem in *this* surface. Grep hits are candidates, not findings: open the file and read the context.
3. **Fix** - one concrete correction using existing tokens/components.

Before the plan, run a **falsify pass**: re-open each finding's file and try to prove it wrong (is it handled elsewhere? a wrapper? the primitive already does it? deliberate per DESIGN.md?). If it's wrong, set `rejected` with the reason. Never delete rows.

## 4. Coverage ledger and machine verification

An agent that writes "clean" has proved nothing; an agent whose claims a script re-checks against the files has. So the coverage ledger is generated, filled and **verified by script**:

```bash
node <skill>/scripts/verify_ledger.mjs init  .ui-audit/<slug> [--categories LAY,RSP]   # FULL: all rules; FOCUSED: mapped categories
node <skill>/scripts/verify_ledger.mjs check .ui-audit/<slug> --gate g1               # same --categories as init
```

`init` writes `04-coverage/01-layout-hierarchy.md` … `05-craft-copy.md` with every rule ID already listed in catalog order and status `TODO`. The agent only replaces each `TODO` and fills the Evidence cell, so omitted, reordered or invented rule IDs are impossible. The section-to-category map lives in the script.

| Status | Evidence cell must contain | What `check` does |
|---|---|---|
| `PASS` | `path:line "verbatim code"` (≥6 chars) | opens the file, fails unless the quote is within 5 lines of the line |
| `VIOLATION` | `F-001[, F-002]` | each F-id must exist in `03-findings.md` under this same rule ID, and each finding's rule must be marked `VIOLATION` |
| `N/A` | `grep:/regex/ reason` (reason ≥15 chars) | runs the regex over every inventory file; any hit fails ("the mechanism is absent" must be true) |

Also checked: no `TODO` left; the same `path:line` cited for more than 4 rules (rubber-stamping) fails; findings must quote real code at their `file:line`. A pass prints a **spot-check list** of random `PASS` rows: the independent verifier (§6) re-reads those lines and judges whether the code really satisfies the rule. The script proves the evidence exists; the spot-check proves it means what is claimed.

What the script cannot prove: a quote that exists but does not satisfy the rule, or a violation nobody noticed. That is why the second reader (§6) and the falsify pass remain mandatory, and why severity is rated after the hunt.

`PASS` without a quote, "all clean" lines, a hand-written row order or a stamp not produced by the script fail G1 by definition. FOCUSED mode runs both commands with `--categories` for the categories mapped in `00-scope.md`.

## 5. Red flags and rationalizations

If you catch yourself thinking one of these, stop and do the step.

| Thought | Reality |
|---|---|
| "I will design wireframes without understanding who uses the app" | Blind design creates toy interfaces. Classify archetype and audience in 01-design.md first. |
| "I don't need external research, I know what SaaS looks like" | Domain research reveals table patterns, compliance flows, and real user expectations. Run search_web or doc checks. |
| "I will style concepts from memory, close enough to DESIGN.md" | Concepts from memory are hallucinations. Build the token ledger first; every value in `concepts/` must cite a ledger row or G2 fails. |
| "I will invent toast and error text for the prototype" | Prototype copy must be verbatim from the codebase or `PLAN.md` §7. Invented codes and generic success text fail G2. |
| "I will skip antislop skills" | Always load antislop, antislop-ui, antislop-copywriting, antislop-human, antislop-layoutmobile, antislop-code if available in the environment; otherwise skip. |
| "It's a small page, I'll skip the ledger" | Small pages still have dialogs, states and mutations. The ledger takes minutes. |
| "I read the main file, I get the idea" | Gate G1 needs every inventory file read. Bugs live in the child components and dialogs. |
| "Grep found nothing, so the category is clean" | Grep finds candidates. A clean rule needs a `PASS` row whose quote the script can find, or an `N/A` regex that matches nothing. |
| "I checked every rule" (no script output) | Claims count only as the script's PASS line pasted in this message. Run `verify_ledger.mjs check`; fix every FAIL; never edit the script or the ledger shape to make it pass. |
| "I'll cite the same line for the similar rules" | Rubber-stamping fails the check (max 4 rules per `path:line`). Each rule needs the code that satisfies it. |
| "The runtime scripts found nothing" | `ui_audit.mjs` and `scan_patterns.mjs` produce candidates only; they never close a rule. |
| "The user wants a tweak, I'll build a second concept for comparison" | One concept, edited in place; log each tweak in the Revision log (interactive-prototypes.md §6). |
| "The screens look fine, so the flow between them is fine" | Flow bugs live in transitions, not screens: walk each step's advance, validation gate, and failure landing (FLW-01..04), and record the flow table in `PLAN.md` §4b. |
| "The user asked for a redesign, not bug fixes" | In FULL mode the audit covers everything; bugs found go in the ledger. In FOCUSED mode they go in "Noticed, out of scope". Either way they're written down. |
| "The user asked for X only, but Y is also bad, I'll fix it too" | FOCUSED means focused. Log Y under "Noticed, out of scope", don't touch it. |
| "This is obviously fine, no need to verify" | Every `fixed` row needs a verification line in `06-verify.md`. |
| "Approval is implied, they asked me to do it" | G3 needs explicit approval in this conversation, unless the user said up front not to wait (quote it). |
| "The existing skeleton is fine, no need to touch it" | When UI layout or card structure changes, the old skeleton mismatches the new layout and causes layout shift (CLS). Skeletons must be redesigned to match the new UI. |
| "I'll update the ledger at the end" | Update as you go; end-of-task reconstruction is where steps get faked. |
| "Typecheck probably passes" | Run it in this message and paste the result. |
| "Should work now" / "Looks good" | Evidence before claims. Say what you ran and what it returned. |
| "The checklists passed once, so it's done" | The audit is a loop, not a one-shot pass: re-audit each changed surface against the SLOP and MOT rules its slices touched and fix any regression before G5. |

## 6. Context resets and long runs

- After a context reset or `/compact`, re-read `00-scope.md`, `03-findings.md` and `05-progress.md` before doing anything else, and continue from the first unfinished slice.
- **Parallel audit with subagents (use when the Agent tool is available; the default for FULL mode).** The five coverage section files are independent, so spawn up to five read-only subagents in one turn, one per section (or per category group for FOCUSED). Each gets: the section's generated skeleton (its rule IDs), the `02-inventory.md` file list, the evidence grammar (§4), and the instruction **"return the full coverage table and a findings table as text in your final message; do not write files"** (subagents are refused when they write report files). Each reply must open with `Audited by: <agent/model>; files read: <paths>`. The lead then:
  1. writes each reply into its `04-coverage/<section>.md` under an `Audited by:` line (the script fails `TODO` or a missing line), and renumbers subagent finding ids (`T-1`…) into the next free `F-xxx`;
  2. **falsifies every negative claim** ("missing", "absent", `N/A`, `VIOLATION`) by re-opening the cited code before accepting it (one auditor once claimed a rate limiter did not exist when it was at `post-document.ts:76-85`);
  3. runs `check --gate g1` and fixes FAILs itself or re-dispatches only the failing section.
  The lead still owns the ledger, the falsify pass and the gates. No Agent tool: audit the sections yourself in order and write `Audited by: lead`.
- **Independent verifier (mandatory at G1 and G5).** Hand a fresh subagent only the spot-check list printed by `check` (rule text from the catalog + cited file:line) and ask, per row: "does this code satisfy this rule? agree / disagree + one line". Any disagreement reopens that whole category. For G5, give it `PLAN.md`, `03-findings.md` and the diff and ask which `fixed` finding the diff does not actually fix; it rates severity before seeing the ledger's ratings. No subagent available: do the same re-read yourself as a separate pass and say so in `06-verify.md`.
- After a reset, re-run `verify_ledger.mjs check` for the last passed gate before trusting the files on disk.
